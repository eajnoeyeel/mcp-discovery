# CallNavi

> 출처: arXiv:2501.05255 (2025)
> 한 줄 요약: LLM의 API 라우팅과 파라미터 생성 능력을 분리 평가하는 벤치마크를 제시하고, 라우팅-파라미터 분리 하이브리드 접근이 단일 모델보다 우수함을 보인 연구.

---

## 해결하려는 문제

기존 LLM 도구 사용 벤치마크는 후보 API가 5개 미만으로 적고, 라우팅(도구 선택)과 파라미터 생성을 분리하여 평가하지 않는다. CallNavi는 최대 115개 API 후보에서 올바른 도구를 선택해야 하는 현실적 규모의 벤치마크를 제시하고, 라우팅 정확도와 파라미터 생성 정확도를 독립적으로 측정하여 각 단계의 난이도 차이를 분석한다.

## 핵심 아이디어

- **대규모 벤치마크 구축**: 729개 질문, 579개 API, 10개 도메인, 3단계 난이도 — 기존 벤치마크 대비 현실적 규모
- **라우팅-파라미터 분리 평가**: LLM의 도구 활용을 라우팅(도구 선택)과 파라미터 생성(입력값 채우기)으로 분리하여 각 단계의 성능과 난이도를 독립 측정
- **모델 비교**: GPT-4o, Gemini, LLAMA, Command-R 등 다양한 모델의 도구 사용 능력 비교
- **하이브리드 접근**: 라우팅과 파라미터 생성을 별도 모델에 맡기는 2단계 분리 아키텍처의 효과 검증

## 방법론

- **벤치마크 구성**: 729개 질문, 579개 API 함수, 10개 도메인 (Banking, Shopping, Logistics, Aviation, Healthcare 등)
- **난이도 3단계**: Easy(456, 단일 API), Medium(188, 다중 순차 API), Hard(85, 중첩 의존 API, 최대 5단계)
- **핵심 도전**: 질문당 최대 115개 API 후보에서 필터링 없이 직접 선택 (기존 벤치마크 <5개와 차별)
- **평가 메트릭**: Exact Match (API 라우팅), AST Match (파라미터 정확도), GPT Score (종합)
- **Backward Thinking**: 최종 필요 API에서 역추적하여 의존 API 체인 구성

## 주요 결과

### 모델별 종합 성능

| 모델 | Exact Match (라우팅) | AST Match (파라미터) | GPT Score |
|------|---------------------|---------------------|-----------|
| **GPT-4o** | **0.919** | **0.711** | **0.913** |
| GPT-4o mini | 0.913 | 0.710 | 0.908 |
| Gemini 1.5 Flash | 0.908 | 0.604 | 0.876 |
| LLAMA 3.1-70B | 0.861 | 0.245 | 0.583 |
| Command-R-35B | 0.781 | 0.134 | 0.400 |

### 난이도별 성능 저하 (GPT-4o)

| 난이도 | Exact Match | AST Match |
|--------|-------------|-----------|
| Easy | 0.978 | — |
| Medium | — | — |
| **Hard** | **0.611** | **0.388** |

### Backward Thinking 효과 (Hard tasks)

| 모델 | Before | After | 개선율 |
|------|--------|-------|--------|
| GPT-4o | 0.388 | **0.729** | **+87.9%** |
| GPT-4o mini | 0.364 | 0.482 | +32.4% |

### JSON vs YAML 형식 영향

| 형식 | LLAMA 3.1 Syntax Accuracy |
|------|--------------------------|
| JSON → JSON | 0.925 |
| YAML → YAML | 0.525 |

JSON 형식이 YAML 대비 일관적으로 우수

### 핵심 발견

- **라우팅은 쉽고, 파라미터 생성은 어렵다**: 대부분의 모델에서 Exact Match(라우팅) 0.78+ 달성, 반면 AST Match(파라미터)는 큰 격차 존재 (GPT-4o: 0.919 vs 0.711)
- 라우팅과 파라미터 간 점수 차이는 **각 태스크의 난이도 차이**를 반영하는 것이지, 도구 설명의 어떤 구성 요소가 더 중요한지를 의미하지 않음
- **2단계 분리 하이브리드**(GPT 라우팅 → 전문 모델 파라미터 생성)가 단일 모델보다 우수 (Section 7.1)
- **Hallucination 문제**: Phi3 14B가 존재하지 않는 API 생성 ("getLostBaggageReport")
- **컨텍스트 길이**: 4K 토큰 모델은 6K+ 입력에서 truncation → 불완전한 API 호출

## 장점

- **단계 분리 분석**: 라우팅과 파라미터 생성을 분리하여 각 단계의 난이도를 독립적으로 측정
- **현실적 규모**: 질문당 최대 115개 API 후보 — 기존 벤치마크(<5개)와 차별화된 현실적 난이도
- **다양한 모델 비교**: 상용/오픈소스 모델 전반에 걸친 체계적 성능 비교 제공

## 한계

- 도구 설명 품질과 라우팅 성능의 직접적 인과 관계는 실험하지 않음 (설명 조작 실험 미수행)
- 10개 도메인에 한정, MCP 프로토콜 특화 평가 없음
- 라우팅과 파라미터 생성의 분리가 모든 시나리오에서 최적인지 미검증
- Backward Thinking이 Easy/Medium 태스크에서의 효과는 미보고

## 프로젝트 시사점

이 논문은 description component ablation(도구 설명의 어떤 구성 요소가 라우팅에 중요한지 분석)을 수행하지 않았으므로, **DQS 가중치 설계의 직접적 근거로 사용할 수 없다**. 논문의 핵심 기여는 라우팅과 파라미터 생성이라는 두 태스크의 난이도 차이를 정량적으로 보인 것이며, 이는 아키텍처 설계에 참고할 수 있다.

## 적용 포인트

- **라우팅 vs 파라미터 분리 아키텍처**: 향후 검색/추천 시스템에서 라우팅 단계와 실행 단계를 분리하여 최적화하는 아키텍처 설계 참고 (Section 7.1)
- **Backward Thinking 참고**: Hard 태스크에서 AST Match(파라미터 정확도)가 0.388 → 0.729로 +87.9% 개선 — 역추적 기반 의존성 해결 접근법의 유효성
- **DQS 가중치 근거로는 부적합**: 논문은 description component ablation을 수행하지 않았으므로 DQS 가중치 설계의 직접적 근거로 사용할 수 없음
